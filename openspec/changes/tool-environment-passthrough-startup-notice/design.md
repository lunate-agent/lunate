## Context

The pass-through list is configured in one place — `ToolEnvironmentPassthrough.Configure` — from
resolved settings in three entry points. Its return value already carries the admitted names (the
normalized list) and the credential-name collisions. Only the collision half is rendered today.

```
InteractiveSession ─┐
PrintMode          ├── resolved AgentSettings.ToolEnvironment.Passthrough
AcpMode            ┘            │
                                ▼
                  ToolEnvironmentPassthrough.Configure(names)
                     │ admitted names            │ collisions
                     ▼                           ▼
   ChildProcess.BuildEnvironment      AdmissionNotice(names) ──► Info startup line
                                      CollisionWarning(collisions) ──► Warning line
```

`ChildProcess.BuildEnvironment` reads `ToolEnvironmentPassthrough.Names` where the policy is built;
the new line is a presentation concern at the same three entry points and never reaches a spawn
site.

## Goals / Non-Goals

**Goals:**

- A non-empty admitted list produces one startup line naming the exact variables, in configured
  order, in the interactive session, print mode and ACP mode.
- The line is independent of the collision warning; a collision yields both lines.
- An empty list stays silent.
- The docs state the consequence: the model can read an admitted variable from a command it runs.

**Non-Goals:**

- No change to the strip, exact-name matching, the user-scope rule, or the collision warning.
- No new setting, no change to what reaches the child environment.
- No new ADR: behaviour follows ADR-0035's admitted set and adds only how it is surfaced.

## Decisions

- **Render from the normalized admitted list, not the raw setting.** `Configure` returns the names
  it installed (trimmed, de-duplicated, in order), so the line names exactly what a tool child can
  receive. Alternative rejected: re-reading `settings.ToolEnvironment.Passthrough`, which could
  disagree with the list after normalization.
- **An empty list yields no line.** The admission is only worth stating when something is admitted;
  a default install gains no noise. `AdmissionNotice` returns an empty string and the call sites
  skip it.
- **Info level for the admission, Warning for the collision.** Admission is a statement of state;
  the collision remains the warning, unchanged and still one line.
- **All three entry points share the helper.** `InteractiveSession.ApplyToolEnvironment`,
  `PrintMode.ApplyToolEnvironment` and `AcpMode`'s settings branch call the same
  `AdmissionNotice`, so the wording cannot drift between frontends.
- **Docs:** one sentence in `docs/configuration.md`'s generated row source and one in the
  `docs/guide.md` bullet. The row is regenerated by `scripts/docs-sync`, never hand-edited inside
  the generated region.

## Risks / Trade-offs

- Re-resolution after a wizard commit or login emits the line again. That is the same moment the
  list is re-installed, so the statement stays true; it is not a second startup line on a normal
  start.
- Printing variable names on stderr in print mode is visible output, but it names configuration the
  user wrote, not a value. No value is ever printed.

## Migration

None. No setting changes; a user who configured nothing sees no new line.
